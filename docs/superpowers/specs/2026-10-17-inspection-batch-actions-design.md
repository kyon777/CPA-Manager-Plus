# 巡检页批量凭证操作与安全封禁删除设计

**日期：** 2026-10-17
**范围：** CPA Manager Plus（CPAM）二改；不修改 CPA Core / `cli-proxy-api`。
**状态：** 已获方案确认，等待书面规格复核。

## 1. 背景与问题

健康巡检的“重新登录”结果页已经能展示需要处理的 Codex 凭证，但没有和凭证列表一样的当前页批量更新、当前页封禁账号删除入口。与此同时，凭证列表已有的“删除当前页已封禁账号”会逐个文件执行“全量认证清单读取 → 删除前身份验证 → 删除”，在大量认证文件时反复扫描 CPA，造成几十个文件删除也要等待很久。

已确认的服务端日志显示，单次 `/v0/management/auth-files` 获取可能耗时约 5–22 秒。现有逐文件串行路径会把这类全量读取放大到约每个文件两次，因此慢点是重复全量预检，而不是删除单个文件本身。

## 2. 目标

1. 保留凭证列表已有的两个批量按钮及其入口位置，不移除、不降级其能力。
2. 在健康巡检的 **“重新登录”** 筛选结果工具栏中新增：
   - `更新当前页凭证 (N)`；
   - `删除当前页已封禁账号 (N)`。
3. 将两个页面的“删除当前页已封禁账号”统一改走 CPAM Manager Server 的安全批量删除路径：一次 CPA 清单预检、文件级锁、最多 4 路独立物理文件删除。
4. 只删除已被 Manager Server 记录为 `account_banned` 的目标；普通 401、待恢复、恢复中、其他失败原因都不得删除。
5. 不触发主动额度查询、不重跑巡检、不修改计费、用量、优先级或 CPA Core 的调度逻辑。

## 3. 非目标

- 不删除健康巡检现有的 `删除需重新登录账号` 按钮；新按钮与它并存。
- 不以“当前显示为重新登录”作为封禁判定依据；必须有 Token Recovery 的明确 `account_banned` 终态证据。
- 不把前端并发提高到任意数量，也不以多个浏览器请求并发删除来替代服务端校验。
- 不改 CPA Core API、认证文件存储格式、`usage.sqlite` 计费数据或容器/服务部署结构。

## 4. 用户界面与交互

### 4.1 显示条件

`CodexInspectionResultsPanel` 仅在当前操作筛选为 **“重新登录”** 时，在现有“复制当前页账号”右侧、既有“删除需重新登录账号”之前新增两个按钮：

1. `更新当前页凭证 (N)`
2. `删除当前页已封禁账号 (M)`

其中：

- `N` 是当前巡检分页内可构造 Token Recovery 目标的 Codex 账号数。
- `M` 是当前巡检分页内、Manager Server 已记录最终恢复失败原因为 `account_banned` 的账号数。
- 若 `N` 或 `M` 为 0，对应按钮禁用并清晰显示 `(0)`；不隐藏其他既有按钮。
- 非“重新登录”筛选时，新增的两个按钮不显示。

巡检页与凭证列表共享同一套“当前页”定义：由当前筛选结果和当前页码/页大小得出的 `pageItems`，不会误操作全量巡检结果。

### 4.2 更新当前页凭证

点击 `更新当前页凭证 (N)`：

1. 从当前页 `pageItems` 中提取 Codex 重新登录目标；
2. 使用现有 Manager Server 手动 Token Recovery 批量接口排队；
3. 显示已排队/已跳过/失败的精简汇总；
4. 刷新当前页相关的 Token Recovery 状态，以便人工看到“已自动更新一次”或接口返回原因。

这一步仅提交恢复任务，**不**主动查询额度、历史请求、窗口用量，不自行调用 CPA 巡检，也不改变账号启用状态。

### 4.3 删除当前页已封禁账号

点击 `删除当前页已封禁账号 (M)` 后，沿用凭证列表现有的显式确认交互。确认后把当前页的定位快照发送给 CPAM Manager Server，由服务端完成最终授权与删除；前端不得直接根据本地状态删除。

执行结果按 `deleted`、`skipped`、`failed` 汇总展示。任意单个目标失败不能阻塞其他已经独立验证且可安全删除的物理文件。完成后只失效一次认证清单缓存并刷新一次相关列表状态。

## 5. 服务端安全批量删除设计

新增 Manager Server 认证文件批量删除端点：

```http
POST /v0/management/auth-files/delete-account-banned-batch
```

请求体仅包含当前页定位快照，示意：

```json
{
  "targets": [
    {
      "logical_name": "alice@example.com.json",
      "physical_name": "shared-codex.json",
      "source_index": 0,
      "email": "alice@example.com"
    }
  ]
}
```

客户端传来的名称只是定位线索，绝不是删除授权。Manager Server 对每个目标执行以下顺序：

1. 根据当前管理密钥认证请求。
2. 在自身 Token Recovery 存储中确认该逻辑凭证的最新终态为人工可见的 `account_banned` 错误；缺失、过期、非终态或错误代码不匹配均放入 `skipped`。
3. 对本次候选集合向 CPA 读取 **一次** 认证文件清单，建立不可变的当前快照。
4. 校验逻辑名、邮箱、源索引、物理文件成员关系均仍与快照一致；任何不一致的目标放入 `skipped`，不使用旧快照强删。
5. 按物理文件分组。若一个物理 JSON 中存在任何未被本批次完整选中且同样通过 `account_banned` 验证的成员，则整个物理文件拒绝删除，避免删除共享 JSON 时误伤其他账号。
6. 对全部合格物理文件以稳定排序取得现有 auth-file mutation coordinator 的文件级锁。锁粒度是物理文件名，不使用全局删除锁。
7. 在保持锁的前提下，最多 4 个 worker 并发删除不同物理文件。单个物理文件始终只删除一次；同名文件及并发更新/上传会由同一文件锁串行化。
8. 所有 worker 结束后统一失效一次认证清单缓存，并返回逐项目结果。

响应模型：

```json
{
  "requested": 8,
  "deleted": [
    { "physical_name": "alice.json", "logical_names": ["alice@example.com.json"] }
  ],
  "skipped": [
    { "logical_name": "bob@example.com.json", "code": "not_account_banned", "message": "最新恢复记录不是 account_banned" }
  ],
  "failed": [
    { "physical_name": "carol.json", "code": "upstream_delete_failed", "message": "..." }
  ]
}
```

现有单文件删除仍保持现有行为；新端点在已获得的一次快照上构造已验证删除目标，避免每一个文件再次调用完整清单解析路径。

## 6. 前端状态与复用边界

### 6.1 巡检页

`CodexInspectionPage` 负责从当前巡检 `pageItems` 构造 Recovery 候选；它只向 `CodexInspectionResultsPanel` 传入按钮所需的数量、busy 状态和回调。展示组件不自行请求 CPA，不保存恢复数据库状态。

当前页的 `account_banned` 数量来源于已有 Manager Server Token Recovery 查询结果。若状态尚未加载，按钮保持禁用状态并不推断封禁；加载完成后才显示准确的 `M`。

### 6.2 凭证列表

`AccountsPage` 的两个既有按钮继续原样显示，文案和确认语义不变。其“删除当前页已封禁账号”改用同一 Manager Server 批量删除 API，以获得一次预检与受控并发的性能收益；它不会被迁移、隐藏或替换。

前端会抽取小型的“构建已封禁定位目标 / 解释批量删除结果”辅助逻辑，供两个页面复用，避免两处对 `account_banned` 的字符串判断产生漂移。

## 7. 错误处理与可观测性

- 认证失败、无目标、恢复记录不匹配、清单身份变化、共享文件未完整覆盖均返回结构化 `skipped`，不作为静默成功。
- CPA 删除失败返回 `failed`，其中包含可显示但不泄露 token 的上游错误文本。
- 删除任务会记录批次请求量、已删/跳过/失败数量和耗时，不记录 token、代理凭据或完整 JSON。
- 在前端，结果 toast/消息使用服务器返回的实际原因；不会再笼统显示“删除失败”。
- 若批量接口不可用，前端显示明确错误，不悄悄退回旧的逐项全量扫描路径，避免隐藏性能回退。

## 8. 测试与验收

### 8.1 Manager Server 测试

1. `account_banned` 终态且身份快照匹配时，目标可删除。
2. 401、`credential_not_found`、非终态、缺失恢复记录的目标均被跳过。
3. 一个物理 JSON 含未选中成员时，整文件拒绝删除。
4. 物理文件/邮箱/源索引在快照读取后不一致时，目标被跳过。
5. 一批多个合格文件仅发生一次 CPA 认证清单读取。
6. 多个物理文件删除时并发数不超过 4；同一物理文件只有一个删除请求。
7. 部分失败时其余经过验证的文件仍完成，响应准确区分 `deleted`、`skipped`、`failed`。
8. 批量成功或部分成功后认证文件库存缓存只失效一次。

### 8.2 Web 测试

1. 巡检页只有“重新登录”筛选显示两个新增按钮。
2. `更新当前页凭证` 只提交当前页的可恢复 Codex 目标，不触发额度/巡检请求。
3. `删除当前页已封禁账号` 仅提交当前页 `account_banned` 目标。
4. 凭证列表原有两个按钮仍渲染，删除行为改走批量端点且确认流程保留。
5. 批量结果能展示已删、跳过和失败的真实数量与原因。

### 8.3 人工验收

- 巡检完成后切换“重新登录”并翻页，两个按钮数字随当前页变化。
- 一页混有普通 401 与 `account_banned` 时，删除按钮只计后者。
- 点击“更新当前页凭证”后，账号仍由 CPA 自己后续调度；没有即时额度刷新或计费写入。
- 凭证列表的同名删除操作对几十个独立文件不再执行每文件多次全量清单读取。

## 9. 回滚策略

本次修改局限在 CPAM Manager Server 新端点与 Web 调用路径。若发现异常，可回滚 CPAM 到本次提交前镜像/二进制；CPA Core、认证文件格式、计费数据和运行中 CPA 调度不受本次迁移影响。
