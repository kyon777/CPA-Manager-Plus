# 代理故障替换与批量 Proxy URL 更新设计

- 日期：2026-10-18
- 状态：已完成设计，等待规格审阅
- 范围：仅 CPA Manager Plus（CPAM）
- 不触碰：CPA Core、`cli-proxy-api`、账号 Token、计费与用量采集逻辑

## 1. 目标

在不影响现有凭证调度、计费、额度采集和 Token 字段的前提下，完成两个共享同一服务端能力的功能：

1. 健康巡检识别出带 `proxy_url` 的账号发生疑似代理链路故障后，管理员可以人工确认地批量替换代理，并且只复检本批成功更新的账号。
2. 凭证列表多选账号后，管理员可以批量修改 `proxy_url`：统一写入同一个代理，或从已保存代理池轮换分配代理。

该功能必须适用于上千账号和大量代理 URL；浏览器刷新、关闭或切换页面不得中断已确认的服务端任务。

## 2. 已确认的产品决策

| 项目 | 决策 |
| --- | --- |
| 巡检触发 | 单次命中代理链路失败即标记为“疑似代理异常” |
| 自动化边界 | 绝不自动改账号；必须由管理员确认替换 |
| 代理复用 | 允许无限复用同一正常代理 |
| 失败代理 | 保留在保存的代理列表中，但标记为“疑似失效”，默认不再参与自动分配 |
| 恢复失败代理 | 只能由管理员手动恢复为正常 |
| 批量修改模式 | 同时支持统一设为同一代理、从保存代理池轮换分配 |
| 复检范围 | 仅复检本次成功写入 `proxy_url` 的账号 |
| 新代理复检失败 | 保留新代理，并将它标记为疑似失效；不回滚旧代理，不自动无限换下一个 |

## 3. 非目标

本次不实现：

- 自动替换或自动无限重试代理；
- 修改 CPA Core 或要求 CPA Core 暴露新接口；
- 修改 `refresh_token`、`access_token`、`id_token`、`note`、`priority`、启停状态；
- 主动查询额度、刷新计费数据、触发用量采集；
- 清空账号代理的批量操作；该操作如需支持，应单独设计并要求更高等级确认；
- 将 CPAM 变成第二份账号代理真相。账号 JSON 中的 `proxy_url` 仍然是唯一生效值。

## 4. 当前基础与约束

- 已保存代理列表已经保存于 Manager Server，可跨浏览器、跨电脑使用。
- 凭证列表已有批量字段写回链路，可通过 CPAM 代理到 CPA 的 `PATCH /v0/management/auth-files/fields`。
- CPA Core 在管理 API 调用时会优先使用被选中凭证的 `proxy_url`；CPAM 无需改变 CPA Core。
- 现有巡检遇到 CPA 管理 API 链路错误时通常表现为 `request_error`。CPA 对代理连接失败及部分底层网络失败可能统一返回 `502 {"error":"request failed"}`，所以 UI 与状态必须使用“疑似代理异常”，不能称为确定代理失效。
- 现有账号代理筛选的 URL 规范化逻辑会去除周围空白和末尾 `/` 差异；新功能必须复用等价的规范化语义。

## 5. 架构

### 5.1 统一模块

新增 CPAM 内部的“代理池状态与替换任务”模块，供巡检页和凭证列表共同使用：

```text
保存代理 URL 列表
        │
        ├─ 代理池状态（正常 / 疑似失效）
        │
巡检结果 ─┴─> 替换计划预览 ─> 管理员确认 ─> 服务端替换任务
                                                   │
                                                   ├─ 受控并发写回 proxy_url
                                                   ├─ 仅巡检来源任务的成功写入账号
                                                   └─ 持久化进度与结果
```

该模块只在 CPAM 内运行，通过既有 CPAM → CPA 管理接口写回账号字段；不直接改动 CPA Core。

### 5.2 持久化模型

现有保存代理列表继续作为唯一“代理池来源”，不迁移、不替换，也不影响当前“筛选未使用代理 URL”功能。

新增 CPAM SQLite 表或等价的受迁移管理的持久化实体：

1. `proxy_pool_state`
   - `proxy_fingerprint`：规范化 URL 的不可逆指纹；不在状态表重复保存代理认证信息；
   - `status`：`normal` 或 `suspect`；
   - `last_failure_at`、`last_failure_reason`、`updated_at`；
   - 管理员恢复后将状态改为 `normal`，保留更新时间。

2. `proxy_replacement_tasks`
   - 任务 ID、来源（巡检恢复 / 凭证列表统一更新 / 凭证列表代理池分配）；
   - 状态（草稿预览、待确认、执行中、已完成、部分完成、失败、已过期）；
   - 创建与完成时间、目标总数、成功/失败/跳过/复检统计。

3. `proxy_replacement_task_items`
   - 任务 ID、账号身份快照、原代理与新代理的安全引用、写入/复检状态、具体错误；
   - 映射在预览时生成并冻结，确认后按同一映射执行。

任务草稿在确认前有短期有效期；过期草稿不能执行，必须重新预览，以避免代理池状态或账号状态变化后继续使用陈旧映射。

### 5.3 代理 URL 规范化

所有匹配、去重、状态索引和候选排除均使用同一规范化函数：

- 去掉首尾空白；
- 忽略末尾一个或多个 `/`；
- 空值不进入代理池；
- 保留协议、认证信息、主机、端口和路径的原始语义；不擅自改写 URL。

状态索引仅保存规范化 URL 的指纹；原始 URL 仍由已有保存代理列表和账号 JSON 提供。

## 6. 疑似代理异常分类

巡检不会改变原有建议操作（保留、重新登录、启用、禁用等）的判断，也不会影响 CPA 调度。

账号仅在同时满足下列条件时增加“疑似代理异常”标记：

1. 账号自身当前存在非空 `proxy_url`；
2. 巡检出现 CPA 管理 API 的请求链路失败，例如已知的 `HTTP 502 + {"error":"request failed"}`、连接超时、CPAM 调用上下文超时；
3. 失败不是认证、额度或业务响应类型。

以下永远不得进入代理替换流：

- HTTP 401 与重新登录类认证失败；
- HTTP 429 限流；
- 月限额、5 小时额度、7 天额度、Credits 相关结果；
- 已成功返回的业务 HTTP 5xx；
- 无 `proxy_url` 的账号。

命中分类后：

- 巡检结果保留完整原始错误与原有建议；
- 为该 `proxy_url` 对应指纹写入/更新 `suspect` 状态；
- 绝不自动修改账号文件或自动发起重新巡检。

## 7. 候选代理分配规则

### 7.1 候选构建

针对每个替换任务：

1. 读取保存的代理 URL 列表，规范化并去重；
2. 排除空 URL、状态为 `suspect` 的代理、目标账号本次刚失败的旧代理；
3. 根据当前全部已启用账号的 `proxy_url` 计算占用集合；
4. 将剩余正常代理分成：
   - 优先池：当前未被已启用账号占用；
   - 回退池：已被已启用账号占用但状态正常。

### 7.2 分配

- 第一轮优先按稳定顺序让优先池中的每个代理各分配一次；
- 仍有目标账号时，再从“优先池 + 回退池”组成的全部正常候选中按稳定顺序轮换；
- 同一代理允许分给无限多个账号，因此第二轮可以复用优先池、回退池中的任一正常代理；
- 为避免每一批总从第一条代理开始，轮换起点根据任务 ID 稳定偏移；
- 若候选集合为空，任务预览必须明确显示“没有可用候选代理”，且确认执行按钮不可用；
- 映射创建后冻结，执行阶段不重新洗牌。

## 8. 健康巡检 UI 与流程

### 8.1 巡检结果分类

健康巡检结果标签栏新增：

```text
全部 | 重新登录 | 删除 | 禁用 | 启用 | 保留 | 代理异常
```

“代理异常”仅展示带有前述标记的账号结果，不替代既有“重新登录”等主分类。

### 8.2 替换与复检

“代理异常”结果页新增操作：

```text
更换代理并复检 (N)
```

点击后服务端创建待确认预览任务。弹窗展示：

- 待处理账号数；
- 正常未占用代理数；
- 正常已占用、可回退复用代理数；
- 已排除的疑似失效代理数；
- 映射表：账号、原代理、新代理、分配来源；
- 大量映射的分页浏览与完整映射复制；
- `确认替换并复检` 操作。

确认后，任务按第 10 节的并发与快照规则写回字段。只有写入成功的账号进入定向复检。巡检页展示逐项终态：

- `代理已更新，复检成功`；
- `代理已更新，复检失败：<具体原因>`；
- `代理更新失败：<具体原因>`；
- `账号代理已被其他操作修改，未覆盖`。

原始巡检失败原因必须保留可查看，不能被复检结果覆盖掉。

## 9. 凭证列表 UI 与流程

多选账号的工具栏新增：

```text
批量修改代理 URL
```

弹窗包含两个模式。

### 9.1 统一设为同一代理

- 管理员粘贴一个代理 URL，或从保存代理列表中选择一个；
- 清楚显示“将覆盖 N 个账号当前代理”；
- 提交后只写每个选中账号的 `proxy_url`；
- 不触发健康巡检、额度刷新、计费或用量采集。

### 9.2 从保存代理池轮换分配

- 复用第 7 节的候选和分配规则；
- 显示映射预览并要求确认；
- 确认后只更新选中账号的 `proxy_url`；
- 不自动巡检，因为这不是由巡检错误驱动的恢复任务。

## 10. 并发、一致性与任务生命周期

### 10.1 快照校验

任务项生成时记录：

- 账号文件名；
- 账号稳定身份（可用时为 auth index、邮箱等）；
- 当前规范化旧代理；
- 分配的新代理引用。

写入前重新读取并验证身份和旧代理未变化。若管理员、自动更新或其他批处理已修改该账号代理，则跳过该项，不覆盖，并返回明确原因。

### 10.2 受控并发

- 写回按代理分组并使用有限并发，避免一次向 CPA 发起上千个文件 mutation；
- 账号层面接入既有 mutation/锁协调机制，防止两个批处理同时覆盖同一账号；
- 复检只在写回阶段结束后启动，并使用巡检服务现有受控并发，不抢占无界资源；
- 前端仅轮询任务摘要与分页项目结果，不自己执行逐账号写入。

### 10.3 状态与重试

- 服务端任务持续运行，不依赖页面存活；
- 写入失败的账号不得进入复检；
- 新代理复检又命中疑似代理异常时，保留新代理并把其标记为 `suspect`；
- 不自动回滚、不自动取第三个代理、不循环重试；下一轮必须由管理员再次确认；
- 任务完成后返回成功、失败、跳过、复检成功、复检失败的精确数量和逐项原因。

## 11. 写入、安全与审计

每次账号变更使用现有 CPAM → CPA 字段更新能力，写入载荷仅允许：

```json
{
  "proxy_url": "<assigned-proxy-url>"
}
```

不允许任务写入任何其他认证字段或账号属性。

日志与任务摘要中：

- 代理 URL 使用指纹或脱敏展示，禁止将含认证信息的完整 URL 写入服务日志；
- 管理 UI 可沿用现有凭证访问授权显示代理值；
- 每个任务记录来源、时间、数量、结果和逐项错误，支持刷新后继续查看；
- 不新开公网匿名接口，沿用管理端认证与权限边界。

## 12. 测试与验收

### 12.1 单元测试

- URL 规范化、末尾 `/` 去重、指纹稳定性；
- 候选池：未占用优先、回退复用、排除疑似失效、排除刚失败旧代理；
- 轮换映射的稳定性与任务偏移；
- 代理异常分类：命中合法网络失败；排除 401、429、额度、业务响应 5xx、无代理账号；
- 手动恢复代理状态；
- 统一代理和代理池轮换两个请求的字段白名单。

### 12.2 集成测试

- 创建预览、确认、任务轮询和过期草稿；
- 部分账号写入失败时只有成功项被复检；
- 新代理复检失败后被标记为 `suspect` 且不回滚；
- 并发任务与手工修改同一账号时，陈旧快照被安全跳过；
- 浏览器刷新后任务状态与逐项结果仍可读取；
- 确认所有 CPA 字段 patch 只包含 `proxy_url`。

### 12.3 回归与部署验收

- 现有代理 URL 筛选、保存、恢复、批量优先级、Token 自动更新、巡检和 CPA 用量展示全部保持可用；
- 不修改、不重启、不构建 CPA Core / `cli-proxy-api`；
- CPAM 定向构建和部署前后，核验 CPA Core 身份不变；
- 不向上游仓库推送；后续仅在私有 `origin/lo/custom` 推送。

## 13. 成功标准

- 管理员能从上千条巡检结果中快速定位“代理异常”，确认后批量替换并仅复检成功变更项；
- 代理 URL 可在凭证列表以统一和轮换两种方式批量更新；
- 代理池疑似失效状态跨浏览器、跨电脑、跨页面刷新保留；
- 失败、部分成功、并发冲突均显示可操作的具体原因；
- 代理替换不改变任何 Token、优先级、状态、额度、计费或 CPA Core 行为。
