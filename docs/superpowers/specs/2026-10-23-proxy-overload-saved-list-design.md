# 代理过载统计：已保存列表差集与成功率排序

- 日期：2026-10-23
- 状态：设计已由 LO 确认，待用户审阅本文档后进入实现
- 范围：仅 CPA Manager Plus（CPAM）；不修改 CPA Core、`cli-proxy-api`、计费、调度、巡检或自动更新逻辑。

## 1. 目标

扩展凭证列表的“代理过载统计”弹窗，使操作者可以同时看到：

1. 近三天内具有请求记录的代理及其严格 `server_is_overloaded` 过载统计；
2. 已保存到 Manager Server 的代理列表中、但近三天没有任何请求记录的代理；
3. 可按“成功率”对已统计代理进行升序或降序排序；
4. 对任何可见代理行勾选并复制，一行一个 URL，用于后续人工筛选或调度。

现有“复制授权文件数据”功能必须完整保留，且不与本功能共享请求、状态或选择集合。

## 2. 固定术语与统计口径

### 2.1 观察窗口

- 固定为统计时刻向前 72 小时。
- 每个账号只检查该窗口内最新九条请求证据。
- “有请求账号”表示该账号在窗口中至少有一条请求证据；账号启用状态不是此统计的过滤条件。

### 2.2 严格过载条件

一个账号只在以下三个条件同时满足时计作该代理的“过载账号”：

- 请求失败；
- HTTP 状态为 `502`；
- `header_error_code`（忽略大小写）精确为 `server_is_overloaded`，或 `fail_summary` 含 ASCII 边界完整 token `server_is_overloaded`。

普通 502、EOF、500、503、429、407、401、`not_server_is_overloaded` 均不计作过载。

### 2.3 成功率

本界面的“成功率”仅表示“不触发严格上游过载”的账号比例，并非全部 HTTP 请求的真实成功率：

```text
成功率 = 无 server_is_overloaded 的账号数 / 近三天有请求账号数
```

例如：过载账号 30、无过载账号 40，则成功率为 `40 / 70 = 57.1%`。

### 2.4 URL 归一化

所有差集、分组、选择键均使用相同规则：

1. 去除首尾空白；
2. 忽略末尾一个或多个 `/`；
3. 空字符串被丢弃；
4. 同一归一化 URL 只保留一次，并使用保存列表中的稳定显示值。

因此 `http://proxy:8080` 与 `http://proxy:8080/` 不会被重复统计或错误标记为“未统计”。

## 3. 后端设计

### 3.1 数据来源

现有 `proxy-overload-summary` 服务继续使用：

- 一次 CPA 凭证清单投影：`/v0/management/auth-files?include_proxy_url=1`；
- SQLite 的 `RecentProxyOverloadEvidence` 批量集合查询（每批最多 500 个账号）；
- 已有 15 秒单飞缓存、90 秒服务端工作上限。

扩展时额外从 Manager Server 设置库读取**一次**已保存代理列表（现有 `/usage-service/proxy-filter` 的同一持久化数据）。这只是一个加密设置行的读取，不扫描授权 JSON、不读取 Token、不逐代理请求，也不发起任何代理出口检测。

### 3.2 服务接口与响应

`GET /v0/management/monitoring/proxy-overload-summary` 保持兼容，并增加以下字段：

```json
{
  "saved_proxy_list_available": true,
  "saved_proxy_count": 80,
  "observed_saved_proxy_count": 64,
  "unobserved_proxy_count": 16,
  "unobserved_proxies": [
    "http://proxy-not-used:8080"
  ]
}
```

字段含义：

- `saved_proxy_count`：保存列表中归一化后的唯一 URL 数量；
- `observed_saved_proxy_count`：同时存在于保存列表和本次近三天统计代理中的 URL 数量；
- `unobserved_proxy_count`：保存列表减去上述交集后的数量；
- `unobserved_proxies`：该差集的稳定、去重 URL 列表；
- `saved_proxy_list_available`：设置读取是否成功。

若保存列表读取失败，原有过载统计结果必须仍可返回；该布尔值为 `false`，前端隐藏“未统计”内容并显示稳定的不可用提示，绝不能把空列表伪装成“全部已统计”。

### 3.3 缓存与失效

- 未强制刷新请求仍复用 15 秒缓存；缓存内包含保存列表差集。
- 成功保存代理列表后，`PUT /usage-service/proxy-filter` 明确调用 `ProxyOverloadService.Invalidate()`。
- 下次打开或手动刷新过载弹窗立刻重新计算差集；不会等待 TTL。
- 关闭弹窗仍取消浏览器等待；服务端共享计算不因单个浏览器取消而中断。

### 3.4 安全与隔离

- 所有接口仍使用既有 Manager Server 管理认证。
- 响应仅含代理 URL 和聚合计数；不得出现账号邮箱、文件名、Token、原始错误体或 Trace。
- 不创建数据库迁移、不修改 `usage_events`、不修改 CPA Core 任何接口、状态或计费数据。

## 4. 前端交互设计

### 4.1 弹窗汇总

“代理过载统计”弹窗顶部保留当前统计说明，并补充：

- 已保存代理数；
- 已统计的已保存代理数；
- 未统计代理数。

### 4.2 筛选页签

保留并明确以下筛选：

1. `全部统计`：近三天有请求记录的全部代理；
2. `无过载`：严格过载账号数为零；
3. `有过载`：严格过载账号数大于零；
4. `未统计`：已保存但近三天没有请求证据的代理。

“未统计”不等于代理坏、代理异常或需要替换；它只表示最近三天没有可供统计的请求记录。

### 4.3 表格与排序

统计页签表头为：

| 选择 | 代理 URL | 有请求账号 | 过载账号 | 无过载账号 | 成功率 |
| --- | --- | ---: | ---: | ---: | ---: |

- 默认顺序维持现有逻辑：无过载优先、随后有请求账号数降序、最后归一化 URL 稳定排序。
- 点击“成功率”表头：第一次高到低，第二次低到高，继续点击在两者间切换。
- 成功率相同时，使用现有默认稳定排序作为 tie-breaker。
- “未统计”页签仅展示 URL 和“近三天无请求”；不把 `—` 当作 0% 参与成功率排序。

### 4.4 勾选与复制

- 所有四个页签都支持“全选当前可见项”、单项勾选和复制。
- 复制结果为 LF 分隔的 URL，不含末尾换行；复制仅作用于当前可见项中被选中的行。
- “刷新”仍是手动行为；打开弹窗、切换页签、点击排序、勾选或复制都不会触发自动轮询、凭证列表全量刷新、额度读取、历史用量读取或代理出口探测。

## 5. 性能与不变量

- 不扫描 5000 个授权 JSON 文件；
- 不执行 N+1 凭证/代理请求；
- 不增加任何 CPA 计费调用；
- 不影响已有凭证列表加载、最近请求刷新、历史用量、窗口额度、巡检、自动更新、优先级降级、代理替换或复制授权 JSON；
- 后端只多一次设置行读取和 O(n) 内存集合差集，成本相对已有请求证据聚合可忽略；
- 前端仅对弹窗当前聚合数组排序，不触发账户卡片重新渲染。

## 6. 验证计划

### 后端

- 保存 URL 的尾斜杠、空白、重复项归一化；
- 已保存且近三天无请求的 URL 出现在 `unobserved_proxies`；
- 有普通 502、401、429、503 等请求的代理仍属于“已统计”，但不计严格过载；
- 保存列表写入后缓存立即失效；
- 保存列表读取故障不阻断原有过载统计，且前端得到不可用标记；
- 原始严格 `server_is_overloaded` 判定和 72 小时/最新九条边界不回归。

### 前端

- 四个筛选页签、空态及不可用态；
- 成功率首次降序、再次升序、同率稳定排序；
- 未统计项不参与成功率排序；
- 勾选和复制仅输出所选 URL，LF 分隔且无末尾换行；
- 打开、排序、切换页签不调用额度、历史、运行时元数据或授权 JSON 导出接口；
- 既有“复制授权文件数据”测试与 UI 保持可用。
