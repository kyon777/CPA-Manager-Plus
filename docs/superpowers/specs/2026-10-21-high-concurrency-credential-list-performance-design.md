# 高并发凭证列表性能修复设计

## 目标

在保留以下既有二改能力的前提下，使 4,000+ 凭证、下游高并发请求和持续优先级降级期间的凭证列表保持可操作：

- 全量凭证清单与全局“最近请求”排序；
- 最近 9 次请求的 502/错误筛选；
- 当前可见页的历史请求、价格、额度窗口和 Header 快照展示；
- Token Acquisition、一次自动更新状态、代理 URL、代理筛选、巡检和降优先级策略。

本次只改 CPAM 的 Manager Server 与前端。绝不改 CPA Core、`cli-proxy-api`、CPA 调度、原始凭证、Credits、计费写入或使用事件写入。

## 已确认的瓶颈

服务器 `usage.sqlite` 当前约 29GB、约 251 万条 `usage_events`，投影与索引均为 `ready`。问题不是数据库维护未完成。

1. 全局 `account-recent-index` 把 4,000+ 凭证按 1,000 条分批；当前 indexed 路径会对每个目标分别读取快照与旧身份记录。实测单批约 2.1--5.5 秒。
2. 当前页 `account-window-usage` 以 50 条凭证的额度窗口做聚合；实测约 5.7--7.9 秒。浏览器改变页/筛选时主动中止旧请求，后端把 `context canceled` 错误错误地降级为原始 `usage_events` 查询，最后形成 500。
3. 每 60 秒的被动证据刷新会递增共用 `accountHistoryAutoRefreshRevision`，无论历史或额度窗口是否变化，都会重新触发全局最近索引和当前页窗口用量。
4. 每秒优先级降级轮询本身很快，但出现完成任务时，前端按每条更新在全量数组上 `findIndex`，再替换整个 `files` 数组；高错误率时会反复触发全量行模型、筛选和排序。
5. 恢复状态仅针对可见页查询，但页面顺序变化时会先清空运行时状态 Map，再请求恢复任务，造成“凭证已更新 / 已自动更新一次”短暂消失、重新出现。

## 设计

### 1. 将最近请求索引改为集合查询

保留现有 `POST /v0/management/monitoring/account-recent-index` 契约、1,000 条上限、`recent_limit=1..9`、安全返回字段和全局语义。

仓储层增加集合化 indexed 读取：单个批次将所有目标放入 `VALUES` CTE，以窗口函数为每个 `request_index` 选出最近 N 条。查询仍同时覆盖：

- 物理凭证快照 + `auth_index`；
- 旧 Source 身份兼容；
- Codex workspace/member 身份围栏；
- 既有安全诊断字段。

合并快照和旧身份结果后继续使用现有稳定排序与去重规则。保留旧逐条 indexed 路径作为测试对照，但在线请求走集合路径。结果必须与现有路径等价，不改变最近请求、502 筛选或错误筛选判定。

### 2. 将证据刷新 revision 拆分

新增独立 revision：

- `recentIndexRefreshRevision`：仅在全局最近请求语义需要更新时递增；
- `listWindowUsageRefreshRevision`：仅在当前页额度窗口证据或人工额度操作成功后递增；
- 现有 `accountHistoryAutoRefreshRevision` 继续服务可见页历史，不再作为全局最近索引和列表窗口用量的隐式刷新源。

每 60 秒的 Header 快照/巡检摘要被动刷新不再无条件重启全局最近索引或当前页额度聚合。人工顶部刷新、显式历史刷新、实际凭证变动或真实额度刷新仍会按目标数据域更新。

### 3. 取消窗口用量请求时不降级

`AccountWindowUsage` 的投影读路径若收到 `context.Canceled` 或 `context.DeadlineExceeded`：

- 立即返回该上下文错误；
- 不回退到 `usage_events`；
- HTTP 层把客户端取消识别为取消，不写成服务端 500。

投影真正不可用、schema 不匹配或非取消类数据库失败时，保留现有回退逻辑。正常成功窗口用量、价格和计费展示不变。

前端继续在页/筛选变化时取消过期请求，保留上一份匹配当前页的窗口用量直至新回执完成，避免骨架屏反复清空。

### 4. 降优先级更新采用稀疏批处理

保留每秒 `server-error-priority-demotions/updates` 拉取、二元游标和“本地 priority 必须等于 priorityBefore”安全保护。

前端改为：

1. 将同一短时间片收到的更新去重为 `selectionKey -> priorityTarget`；
2. 仅在一个批次边界提交一次；
3. 使用按凭证 key 的索引表定位，避免每条更新对全量数组线性 `findIndex`；
4. 每次提交只克隆被修改的对象和一次数组容器，维持原有列表全局排序语义。

不改后端队列、降级次数、优先级规则、CPA 写入并发或调度。

### 5. 稳定可见页恢复状态

`useCredentialRuntimeMetadata` 在同一 Manager 连接范围内保留已知 recovery task 状态。目标页切换或排序变化时：

- 只清理不再属于当前可见页的条目；
- 不先把仍命中的状态清空；
- 新回执只在内容真实变化时提交状态。

待处理恢复任务仍以现有轮询继续，但静态“已自动更新一次”不再因无关重渲染闪烁。

## 非目标

- 不把凭证列表重新退回仅服务端分页；全局最近请求排序和筛选继续覆盖完整 inventory。
- 不更改任何 API 计费、usage event 写入、Credits、模型价格或 CPA Core 配置。
- 不删除当前页历史、费用、额度窗口、最近请求可视化。
- 不修改代理检测、代理替换、自动更新、巡检、封禁删除或优先级判定逻辑。

## 验证标准

1. 集合式最近索引与旧逐条路径对同一组混合身份目标给出相同的每账号最近 1/9 条结果。
2. 一个 1,000 账号批次不再执行按账号循环的多次 SQLite 查询。
3. 主动取消 `account-window-usage` 时不触发原始事件回退，也不返回 500。
4. 被动 60 秒刷新不再导致 `account-recent-index` 和 `account-window-usage` 重发；显式数据域刷新仍会发起正确请求。
5. 一批降优先级更新只造成一次凭证数组提交；人工优先级修改仍不会被滞后更新覆盖。
6. 可见页的“凭证已更新 / 已自动更新一次”在同一账号仍可见时不闪烁。
7. 全量最近请求排序、最近 9 次错误筛选、当前页历史/额度展示和计费结果保持不变。
