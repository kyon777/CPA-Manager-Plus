# 300 账号认证 JSON 批量上传设计

## 目标

允许凭证列表通过粘贴 JSON 数组或选择多个 JSON 文件，一次最多处理 300 个账号；Manager Server 使用 8 路受控并发把文件写入 CPA Core，并在超出单次请求大小时自动拆批，同时不触发额度查询、巡检、重新授权或计费数据变更。

## 当前链路与问题

当前链路是：

```text
粘贴 JSON 数组
  -> buildAuthJsonFilePayloads（每条记录生成一个 File）
  -> POST /v0/management/auth-files/batch-upload
  -> Manager Server 异步任务
  -> CPA Core /v0/management/auth-files（逐个串行写入）
  -> 完成后重新读取凭证清单
```

现有约束为：前端 JSON 输入 1,000,000 字符、服务端每批 100 个文件、每批 32 MiB；服务端批量任务按输入顺序串行调用 CPA Core。只提高文件数量上限会把串行等待时间放大，不能解决速度问题。

## 设计决策

### 1. 逻辑批次与传输批次

- 对用户暴露的逻辑上限为 300 个账号。
- Manager Server 的单个异步任务接受最多 300 个文件，单任务总大小提高到 64 MiB。
- Web API 在构造 multipart 请求前按文件数量和总字节数分块；单块最多 300 个文件，安全大小上限为 48 MiB，给 multipart 边界和反代留余量。
- 超过安全大小时自动生成多个子任务，顺序提交并合并结果；用户只发起一次导入操作。
- 单文件仍沿用现有 10 MiB 限制。

### 2. 服务端并发

- `authfilesbatch.Service` 使用服务实例级的 8 个上传槽位，限制所有同时运行的批量任务总并发，不会因为用户同时开多个批次而产生 16、24 路失控请求。
- 每个任务使用 worker pool 消费待上传文件；每个文件仍是独立的 CPA Core 文件写入。
- 任意文件失败只记录安全的文件名和错误文本，不把 Token 内容写入任务状态。
- 任务完成后仅调用一次 `InvalidateAuthFileInventory`；该操作只清理 Manager 的凭证清单缓存。

### 3. 前端行为

- 粘贴解析上限提高到 48 MiB；现有记录数上限 5,000 保留不变，另加 300 条导入业务上限。
- 预处理阶段先完成 JSON 校验、邮箱/文件名去重和必要字段检查，再开始网络上传。
- API 层将多个子任务的 `uploaded`、成功文件名和失败原因合并成一个结果，成功文件不会因另一个子任务失败而被重复提交。
- `useAuthFilesData` 继续在整个逻辑批次结束后最多调用一次 `reloadAfterMutation`；不会在每个文件或每个子任务结束时刷新列表。
- 不新增额度查询、`account-window-usage`、健康巡检、自动重新授权或 Token 更新调用。

### 4. 状态与数据边界

- 新文件上传后保留 CPA Core 返回的状态，通常仍为“待确认”；CPA Core 自己的调度器决定何时巡检和改变状态。
- 清单刷新只读取邮箱、备注、代理 URL、状态等清单投影，不主动向账号发模型请求。
- 不读取、不写入、不迁移 `usage.sqlite`，不改变 Credits、历史用量和计费逻辑。
- 不修改、重启、构建或部署 CPA Core / `cli-proxy-api`。

## 错误处理与可恢复性

- 请求超过文件数或字节数限制时在客户端自动拆批，而不是让整批失败。
- 单个文件失败时保留具体原因和文件名；现有“部分成功/全部成功”提示继续工作。
- 浏览器只等待异步任务状态，不等待 300 次同步上传；轮询超时仍使用现有长等待上限。
- CPA Core 短暂拒绝不会导致已成功文件回滚；后续重试只提交失败文件。

## 验证标准

1. 300 条有效 CPA JSON 可以被接受，所有文件成功后只产生一次前端清单刷新。
2. 301 条在前端被明确拒绝，不发起上传。
3. 总大小超过单块安全阈值时自动拆分，最终成功数等于各子任务成功数之和。
4. 混合成功/失败时失败文件名和错误原因完整显示，成功文件不重复提交。
5. 服务端并发活动上传数始终不超过 8。
6. 新导入文件仍可显示为“待确认”，不会产生额度、巡检或计费请求。
7. 现有单文件上传、CPA 数组转换、代理/备注字段和所有二改功能回归测试通过。
